Product Critique — Context / Tutorial Overlay

2026-05-21 · Focus: use case, scope creep, real users, missing must-haves, and pivots worth considering. Companion to docs/project-audit.md.
TL;DR. The pitch is "live overlay tutorial that teaches while you work." The codebase says you are building a GUI-agent research platform with an overlay glued to the front. The use case as written is too vague to be a wedge, the user is undefined, and ~60% of what is built does not serve the stated product. The features a real user would need to adopt this — sharing, distribution, auth, redaction, multi-OS, browser integration, deterministic targeting fallbacks — none are implemented. Meanwhile you have built a search engine, a VLM grounding stack, and two frontends. Cut hard or pick a different product. There are seven pivots worth considering; section 8 ranks them.

1. The use case — does it survive contact with a real user?

1.1 The pitch (README, verbatim)

"Record a workflow once, replay as a live overlay tutorial. Examples: setting up Git, navigating internal tools, completing multi-step web flows."

1.2 The five-second user test

Three real personas, three honest answers:

Person A — New hire at a 500-person company

Their manager Slacks them a Scribe link. They click it, see numbered screenshots with arrows, follow along in a browser tab while doing the real work in another tab. Done in 4 minutes.

Would they install your Mac app? No. The friction (install native app, grant screen-recording permission, grant accessibility permission, sign in, learn the overlay's UI) exceeds the value of "live overlay" by 100×. The Scribe link won the second the manager copy-pasted it into Slack.

Person B — Senior engineer setting up Git

They run brew install git, paste their SSH key, move on. They will not record a tutorial. They will not watch one. They open Stack Overflow if anything breaks. Your example use case is wrong for this persona — they were never the market.

Person C — A 65-year-old learning Photoshop

This is the only persona who genuinely benefits from a live overlay. They cannot translate a YouTube video into the action in front of them. The overlay solves a real cognitive-load problem.

But: they are probably on Windows. They do not know what a "macOS overlay" is. Their grandchild who might install it for them is not paying for software.

The use case the README claims (developer / employee productivity) is the use case where you lose to Scribe and Loom. The use case where you would actually win (accessibility / cognitive-assist) is not what the README or roadmap describes, and the codebase does not optimize for it.

The uncomfortable thought experiment

If you launched today and got 100 signups, what would you ship them?

  1. They install the Mac app. (Lose Windows/Linux users.)
  2. They grant screen-recording permission. (Lose the security-conscious.)
  3. They record a tutorial. Holo enrichment runs. The dataset gets a new row.
  4. They share it with… how? There is no share link. No export. No web viewer. The tutorial lives on disk.
  5. They replay it themselves. The verifier loops on "unsure" (see instruction_verifier.ANALYSIS.md). They give up.

You cannot launch — not because the tech is too hard, but because the distribution loop does not exist. Scribe's entire business is the paste-this-link-in-Slack moment. You have no link.

4. What real users would need — and isn't built

4.1 Distribution and sharing — completely missing

  • Shareable artifact. A URL, PDF, Notion embed — something you can paste into Slack. Without this the tutorial never escapes the recorder's laptop.
  • Web viewer. Replay surface that works without installing the app. Otherwise you are gating your own growth.
  • Browser extension. For web-app tutorials (80% of internal-tools and onboarding flows), a Chrome extension beats a native overlay every time.

4.2 Authoring — half-built

  • Edit after recording. Record once is unrealistic; reality is you mess up step 4 and need to re-record just that step. Not supported.
  • Step narration / annotation. Users need to add "click here because X." Holo's action description is fine for actions, not for teaching.
  • Branching. "If you see this dialog, click Cancel; otherwise continue." Real tutorials need conditional logic.
  • Variables / parameterization. "Enter your email" — you cannot record one user's literal email and replay it for a different user.

4.3 Trust and safety — completely missing

  • PII redaction at record time. Explicitly deferred in README. First time someone records a flow touching a password field, you have a liability problem. Must land before any real user.
  • Secure field detection. type=password fields, 2FA codes, credit cards — must be blocked from frame capture by default.
  • Audit trail. For compliance: who recorded, who replayed, when, did they confirm each step.
  • Data residency. Where do the screenshots live? Who can see them? No answer anywhere in the codebase.

4.4 Cross-platform — abandoned by decision

  • Mac-only forever under current architecture. But: internal-tools market is 60% Windows; browser-app tutorials are OS-agnostic.
  • The "no AX" decision (feedback_no_ax_in_recorder.md) is a portability hedge for portability you will never ship. You pay the accuracy cost today for an option you will not exercise.

4.5 Deterministic fallbacks — missing

  • VLM grounding alone will fail on small targets, occluded targets, custom-rendered apps (Electron, Figma, games).
  • Real systems use a layered approach: AX tree → DOM → OCR → VLM, in that order. You are using only the most expensive and least reliable layer.

4.6 Replay quality — under-invested

  • "Did the app respond?" Currently the user confirms. Real product needs automatic state detection (the verifier exists but per the analysis doc is too unreliable).
  • "What if the app updated?" UI redesigns break recorded tutorials. No re-grounding workflow exists; tutorials decay to garbage in 6 months.
  • Speed control, pause, rewind, skip — none of it in ChatPopupView.swift by inspection.

4.7 Measurement — does not exist

  • No completion-rate tracking. Did the user finish?
  • No drop-off analytics. Which step did they get stuck on?
  • No user-facing A/B variants. (The two A/B flags you have are internal model selection.)
  • No eval suite on a benchmark. docs/eval-harness-changes.html — changes to what baseline?

Without measurement you cannot tell if the overlay beats a Loom. You cannot tell if a planner change helped. You are flying blind.

4.8 Auth, billing, admin — not started

No accounts, teams, SSO, billing, admin console. Not premature — required to ship to anyone but yourself. WalkMe is a $7B company because of these, not because of their overlay.

5. Where you are lacking, ranked by damage

  1. No shareable artifact. You cannot grow without a link to paste. Existential.
  2. No PII redaction. First-customer blocker; legal kills the deal.
  3. No measurement. Cannot improve what you cannot see. The verifier-loop incident is the canary.
  4. No deterministic targeting layer. VLM-only grounding hits a quality ceiling you cannot pass.
  5. No defined ICP. Every other lack is downstream. You cannot prioritize features for a user you have not chosen.
  6. No cross-platform path. Mac-only kills 90% of viable markets.
  7. No editing post-recording. Perfect-or-restart rituals do not survive contact with humans.
  8. No competitive teardown in writing. If you cannot articulate why you beat Scribe in a sentence, the product cannot win.

8.9 What this comparison says

If you optimize for code reuse, pivot 1 (training data) is the clear answer — you keep ~70% of what you have built and the codebase already half-leans this way.

If you optimize for defensibility and ceiling, pivot 2 (compliance) wins, but only if you have access to a regulated industry buyer.

If you optimize for market clarity and fastest user feedback, pivot 5 (Scribe rival) wins, but it requires admitting most of the current code is sunk cost.

The pivot that does not appear on this list is "keep doing what you are doing." That is the one to rule out.

9. Bottom line

The use case as written is too vague to win against the tools that already exist. The user is undefined. The features a real user would need are not built. The features that are built mostly serve a research agenda, not a product.

You are not lacking engineering. You are lacking subtraction, a named user, and a chosen pivot. Until all three happen, every new feature is technical debt with no offsetting customer value.

The path forward is to:
  1. Cut 60% of the code (see Tier 1 kill list).
  2. Name one user — pick a pivot from section 8.
  3. Ship one shareable artifact for that user within 30 days.
Everything else is procrastination dressed up as progress.
